# Polaris - Project Constitution

**Project Name:** Polaris - ELM Metrics Dashboard  
**Created:** January 21, 2026  
**Methodology:** Specification-Driven Development (GitHub Spec Kit)

---

## Core Principles

### 1. Specification First
All development begins with a clear, unambiguous specification that defines WHAT we're building and WHY, not HOW.

### 2. Traceability
Every line of code traces back to a specification requirement. Every metric on the dashboard has a defined purpose.

### 3. Quality Over Speed
We build metrics visibility to improve quality. The tool itself must exemplify quality in its implementation.

### 4. User-Centric Design
Dashboard serves multiple roles (QE Leadership, Dev Leadership, PMs, ICs, Executives). Each view must be intuitive and actionable for its audience.

### 5. SAFE Framework Alignment
Polaris aligns with Scaled Agile Framework principles: transparency, alignment, and built-in quality.

### 6. Integration Excellence
Seamless integration with existing tools (Jira, QTest, code repos) without adding team friction.

### 7. Living Documentation
Specifications evolve. Metrics evolve. The dashboard adapts to organizational changes.

## Technical Values

- **Simplicity**: Prefer simple solutions over complex architectures
- **Performance**: Dashboard loads in < 3 seconds with full data
- **Maintainability**: Code that future developers can understand and extend
- **Testability**: Comprehensive automated testing (our QE team built this!)

---

## Decision-Making Framework

When facing technical or product decisions, ask:
1. Does this serve the user's need to understand quality metrics?
2. Does this align with SAFE principles?
3. Is this the simplest solution that could work?
4. Can we validate this decision with data?
5. Does this make the organization more transparent and aligned?
